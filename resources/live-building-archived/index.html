Public-state guide

Live. Building. Archived.

A practical way to state whether a public page is current, in progress, conceptual, or historical—without confusing an editorial label for a ranking, citation, traffic, or AI-answer control.

Short answer: a public-state label should describe what a reasonable visitor may do now. The useful work is making that state agree across the page, navigation, conversion path, metadata, structured data, canonical URL, sitemap, and review record.

When an offer changes, a prototype becomes public, a course pauses, or an old claim survives its useful life, most teams reach for a label. “Coming soon.” “Legacy.” “Under construction.” “Archive.” The label is often the smallest part of the decision.

The harder question is whether every surface that represents the item tells the same story. A visitor should not need a detective’s mindset to discover that an offer is no longer available. A crawler should not receive a current commercial signal from a page whose visible copy says “historical.”

Four public states

These states are an editorial and operating vocabulary, not a universal platform standard. The distinction matters more than the exact labels: current capability, incomplete work, idea, and historical record should not collapse into one commercial claim.

Public stateReasonable reader inferenceMinimum visible boundaryDefault conversion path
LiveThe item is currently available within stated scope.Scope, owner, current source or service description, and next decision.The relevant consultative or transactional route.
BuildingWork is underway, but it is not a finished offer or dependable public capability.What exists now, what does not, and the next evidence required.No purchase or enrollment implication; a related live route only if truthful.
ConceptualThe page explains an idea, model, or proposal rather than an operating product or service.The concept’s purpose and a plain statement that it is not a current offer.A related educational or consultation route, never a simulated availability signal.
ArchivedThe material is retained for context or history and does not define the current offer.Archive rationale, current alternative where one exists, and a date or record for the boundary.A current resource, a canonical replacement, or no conversion path.

What must agree

Google’s structured-data guidance is useful because it frames the essential constraint plainly:

Visible-to-structured-data parity

“The structured data on the page describes the content of that page. Don't create blank or empty pages just to hold structured data, and don't add structured data about information that is not visible to the user, even if the information is accurate.” [1]

That is a representation rule, not a rich-result guarantee. A visible archive notice paired with current-offer markup is contradictory. So is a page promoted in primary navigation as a live service while its body describes an experiment with no supported access path.

Do not use a label to solve the wrong URL problem

A state label does not replace a redirect, canonical decision, or durable removal decision. These tools solve different problems.

If a page has moved to a relevant current replacement, a permanent server-side redirect can tell people and Google Search that the page has a new location. Google describes permanent redirects as a signal that the redirect target should become canonical. [2] If old and new URLs are duplicate or very similar pages, a canonical declaration can state a preferred URL; Google treats redirects and rel="canonical" annotations as strong signals, with sitemap inclusion as weaker support. Those signals should not conflict. [3]

If a page should remain available as history, redirecting it away may erase useful context. Keep the page reachable, label its state visibly, link to a current successor where one exists, and remove commercial language that no longer applies. If a page should no longer be public, the durable action belongs at the content or access layer. Google’s removal guidance explains that a temporary removal request is not a permanent removal method. [4]

A useful rule

Preserve history when it helps someone understand the record. Redirect when a materially equivalent current destination exists. Remove or restrict access when the content should not remain public.

None of those choices guarantee which URL a search product, browser, referral, answer engine, or assistant will show at a particular time. Google states that a crawl request “does not guarantee that inclusion in search results will happen instantly or even at all.” [5] Treat the technical action as an implementation decision with observable follow-up, not a performance claim.

Use dates as records, not theater

A “last updated” note can be useful when it tells a reader what was reviewed and when. It becomes theater when the date changes without a substantive check. Schema.org defines dateModified as the date a CreativeWork or DataFeed item was most recently modified. [6] That is a date field, not proof that a claim was accurate, complete, or independently reviewed.

For each consequential public state, keep a small record with the state, source, owner, change date, visible boundary, and next review. The record can live in a repository, editorial system, evidence ledger, or versioned document. What matters is that a reviewer can distinguish a claimed date from a documented decision.

Schema.org also has an archivedAt property, but its own documentation marks it as new and shows limited adoption. [7] Use it only when it fits the structured-data model and after validating the markup. It is not a commitment from Google Search or an AI system.

A five-question state review

  1. What can a visitor actually do now? Name the live action, or state clearly that none exists.
  2. Which source makes that state defensible? Link to the current record, change decision, service scope, release note, or public artifact.
  3. Does every visible and machine-readable surface agree? Check page copy, CTA, title, metadata, structured data, canonical URL, sitemap, and internal links.
  4. What is the right treatment for the prior URL? Preserve, redirect, restrict, remove, or leave live—and document why.
  5. Who owns the next review, and what would change the state? A state without an owner or transition condition quickly becomes another stale claim.

The quiet advantage of accurate state

There is no prize for making everything sound active. A small, clearly bounded live surface is more useful than a large site that implies capabilities it cannot presently support. A well-labeled archive can build more trust than a silent redirect. A credible building page can show disciplined work when it names what exists, what remains unproven, and the next evidence needed.

The goal is not to manufacture confidence. It is to make the public record easier for people and systems to inspect before they decide what to do next.
